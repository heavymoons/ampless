Follow-ups to the theme post classes release (heavymoons/ampless#408).

- `ampless`: new `mergePostMetadata(base, mine, theirs)`, a three-way merge of post metadata per top-level key, returning `{ metadata, conflicts }`. Values compare deeply (absent equals absent). A key only one side changed takes that side's value (or its removal); a key both sides changed the same way takes that value. `postClasses` changed differently on both sides is set-merged when base, mine and theirs are each absent or a clean id list: theirs in order, minus the ids mine removed, plus (in mine's order) the ids mine added, so a removal on either side wins and an id added on both sides is kept once; an empty result deletes the key. Any other key changed differently on both sides, or a `postClasses` that is not a clean id list, is listed in `conflicts` (with theirs as a placeholder in `metadata`); callers must not write when `conflicts` is non-empty. A legitimate own `__proto__` key (as `JSON.parse` creates it) is read, merged and returned as an ordinary own key: it survives `JSON.stringify` and never changes the result's prototype.
- `ampless`: new `mergeStaticContent(base, mine, theirs)`, a three-way merge of a static post's `{ format, body, files }` (`files` = `metadata.files`) as one atomic group, returning `{ value }` or `{ conflict: true }`. Groups compare deeply. If mine equals base it takes theirs; if theirs equals base or equals mine it takes mine; otherwise it is a conflict. New exported types `StaticContentGroup` and `StaticContentMergeResult`.
- `ampless`: `updatePost(postId, data, options?)` accepts `{ expectedUpdatedAt }`, a compare-and-swap on the stored `updatedAt` (`null` = no `updatedAt` yet); a mismatch throws the new exported `PostUpdateConflictError`. A provider opts in with the new `PostsProvider.supportsConditionalUpdate: true`, declaring that `update(id, data, { expectedUpdatedAt })` is atomic and throws `PostUpdateConflictError` on a mismatch. **Behaviour change for custom providers:** `updatePost` with `expectedUpdatedAt` on a provider without the flag now fails closed — it throws the new exported `ConditionalUpdateUnsupportedError` and never calls the provider, instead of risking an unconditional write. `updatePost` without options is unchanged (two-argument call), so plain updates and creates on existing custom providers keep working. `supportsConditionalPostUpdate()` reports whether the configured provider has the flag.
- `@ampless/admin`: saving an existing post no longer overwrites metadata that changed after the form was opened (for example `postClasses` set by MCP `update_post`, or a plugin key). The form re-reads the post, merges metadata with `mergePostMetadata` and writes conditionally on the re-read `updatedAt`. Post styles added or removed on both sides are combined. If another key was changed both here and elsewhere, nothing is written and an error names the keys. If the post changes between the re-read and the write, nothing is written, the edits stay in the form and a "save again" message is shown. Other fields stay last-write-wins, as before; creating a post is unchanged. The admin posts provider declares `supportsConditionalUpdate` and implements it with a conditional `updatePost` mutation. With a custom posts provider that lacks the flag, editing a post is refused with an error explaining that the provider must implement conditional updates — it is never saved unconditionally.
- `@ampless/admin`: saving an existing post keeps an own `__proto__` metadata key (for example one a plugin stored) instead of dropping it.
- `@ampless/admin`: when the loaded, edited or stored post is `format: 'static'`, saving merges its bundle manifest (`body`), `format` and `metadata.files` as one group with `mergeStaticContent`, so a stale manifest is never written next to another bundle's `files`. A save that did not change the bundle (for example a title edit) keeps a bundle someone else uploaded meanwhile. If both editors changed the bundle, nothing is written and an error says so; the form keeps its state. On edit, the post is now re-read before a newly picked bundle is uploaded, so a conflicting save uploads nothing and leaves the other editor's files in S3 intact. Non-static posts keep body last-write-wins.
- `@ampless/admin`: restoring a revision applies post styles only when both the revision's and the current `metadata.postClasses` are absent or a clean id list. Otherwise the current stored value (for example a plugin-owned one) is kept and a notice explains why, so restoring a legacy non-array or string value can no longer erase it on save.
- `@ampless/admin`: the preview copies every http(s) stylesheet link of the admin page again, CDN-hosted ones included (as before the post classes release), keeping `integrity`, `crossorigin`, `media` and `referrerpolicy`. Other schemes are skipped. These are stylesheets the admin page already loaded, so no new origin is introduced and the CSP is unchanged.
- `create-ampless`: the bundled `THEMES.md` / `THEMES.ja.md` describe the preview's stylesheets accordingly.
