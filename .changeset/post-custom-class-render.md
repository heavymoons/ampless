Theme-declared custom classes for posts: manifest declaration, rendering, and editing from the admin and MCP (heavymoons/ampless#411; refs #380).

- `ampless`: `ThemeCustomClassTarget` gains `'post'`, so a manifest can declare `{ id: 'wide', label: 'Wide', target: 'post' }`. New helpers `themeCustomClasses(manifest, target)`, `themePostClasses`, `postCustomClassName` (`ampless-post--<id>`), `readPostClasses`, `bypassesPostBodyWrapper` and `postBodyClassName(post, base)`. Post classes live under the namespaced metadata key `POST_CLASSES_METADATA_KEY` (`'ampless:postClasses'`) as a tagged `PostClassesMetadata` value, `{ kind: 'ampless.post-classes', version: 1, ids: [...] }`; anything else under that key is ignored. `themeTableClasses` behaves as before (still table entries only), so the admin table style menu never sees post entries.
- `ampless` (write side): `withPostClasses(metadata, ids)` returns a copy with only that key changed (ids validated and de-duplicated, key removed for `[]`; throws on an invalid id or when the key holds a value that is not a tagged post-classes value, see `hasForeignPostClassesValue`); `postClassesMetadataError(metadata)` validates a caller-supplied tagged value.
- `ampless` (concurrency): `updatePost(postId, data, { expected })` — `expected` is the post exactly as the caller read it — writes only if the stored post still matches it, via a new optional `PostsProvider.updateIfUnchanged`. A mismatch (or a deleted post) throws `PostUpdateConflictError`; when no conditional write is possible (provider without `updateIfUnchanged`, a backend without the conditional mutation, or no `updatedAt`) it throws `ConditionalPostUpdateUnsupportedError` and nothing was executed — it never falls back to an unconditional write. `supportsConditionalPostUpdate()` reports provider support. The two-argument `updatePost` and existing providers are unchanged.
- `@ampless/backend` (new opt-in mutation): `amplessUpdatePostIfUnchanged(postId, patch, expected)` (JSON-string arguments, returns `Post`, admin/editor groups), backed by the new AppSync JS resolver `amplify/data/update-post-if-unchanged.js`. It is one DynamoDB UpdateItem whose condition checks `updatedAt` **and** every field in `expected`, because `updatedAt` alone has millisecond precision and two writes in the same millisecond leave it equal. It validates the patch, REMOVEs fields patched to `null`, leaves `createdAt` and other attributes alone, and always sets a strictly newer `updatedAt` (max(now, previous + 1 ms)). The op is added only when `resolverPaths.updatePostIfUnchanged` is passed explicitly, so a project that bumps `@ampless/backend` without `create-ampless upgrade` still synths without it.
- `@ampless/runtime`: `ampless.postBodyClassName(post, base)` returns `base` plus `ampless-post--<id>` for each valid id in the tagged value. It returns `base` unchanged for posts without it, so existing posts render byte-identical markup. Static posts and no_layout HTML posts (`format: 'html'` + `metadata.no_layout === true`, the middleware's own rule) never get post classes, even with the tagged value: their own URLs bypass the theme wrapper, and the home page featured slot leaves them unchanged too. Ids are re-validated on every call, so values written via MCP / GraphQL cannot break out of the `class` attribute.
- `@ampless/admin`: the post form gets a "Post classes" checkbox group with the active theme's post classes (loaded by `createEditPostPage` / `createNewPostPage` like the table classes). Ids the post has but the theme does not declare are shown as "not in current theme" and can be unchecked. Saving rewrites only `ampless:postClasses`, and only when the selection changed; a value under that key that ampless did not write disables the group and is never touched. Restoring a revision restores its post classes (no other revision metadata). The preview's `<main>` gets the selected classes; without them the preview document is byte-identical to before. The admin posts provider implements `updateIfUnchanged` with `amplessUpdatePostIfUnchanged`, conditioned on every field of the loaded post.
- **Behavior change (`@ampless/admin`)**: saving an existing post is conditional on the post as it was opened (except a static post saved with a new bundle — see "Not addressed" below). If anything changed in the meantime (another tab or editor, MCP, a direct GraphQL write — also within the same millisecond), the save fails with a conflict message instead of overwriting that change; nothing is written and the edits stay in the local draft (static posts have none). On a backend that was not upgraded, the editor falls back to the previous unconditional save but sends it **without** `metadata`, so stored metadata (including concurrently written post classes) is untouched. Switching a no-layout HTML post to another format is saved the same way (the stored `no_layout` flag stays but is inert: every consumer gates it on `format === 'html'`). A save that changes post classes or toggles the no-layout setting on an HTML post is refused with nothing saved. Content fields in that fallback stay last-write-wins, as before.
- `@ampless/mcp-server` (version token, additive): `get_post`, `create_post`, `update_post`, `set_post_classes` and the static bundle tools return posts with a new `version` field, `'v1:' + sha256` of the canonical JSON (sorted keys) of the returned post — postId, title, slug, excerpt, format, body, status, publishedAt, tags, metadata, updatedAt. Any content change changes it, even one that leaves the millisecond `updatedAt` unchanged. Existing fields are unchanged; `list_posts` summaries carry no `version`.
- `@ampless/mcp-server`: `update_post` accepts an optional `expectedVersion`: it re-reads the post, conflicts (nothing written) unless that read's version equals it, then writes through `amplessUpdatePostIfUnchanged` conditioned on every field of that read. Without `expectedVersion` it is the unchanged, unguarded stock update (metadata still replaces the whole object). New `set_post_classes` tool: either `{ postId, ids, expectedVersion }` (full replacement; `ids` without `expectedVersion` is refused) or `{ postId, add?, remove? }` (set operations, no id in both, `expectedVersion` optional). With `expectedVersion` it is version-checked like `update_post`, no retry. `add` / `remove` without it write conditioned on the metadata / format / `updatedAt` read, and on a conflict re-read and re-apply (3 attempts in total). Static and no_layout HTML posts and foreign values are refused; ids are syntax-checked only. Both tools refuse with nothing saved, and never fall back, when the backend lacks the mutation. `update_post` also rejects a tagged post-classes value with invalid ids. `get_schema` documents the key and the guarantees. New `isConditionalCheckFailed` / `isConditionalMutationMissing` / `graphqlErrorsOf` helpers; `GraphqlClient` implementations should attach the GraphQL `errors` array to the thrown error.
- `@ampless/backend`: the MCP Lambda's GraphQL client attaches the AppSync `errors` array (with `errorType`) to the error it throws; the message is unchanged.
- `create-ampless`: the template ships `amplify/data/update-post-if-unchanged.js` and passes it as `resolverPaths.updatePostIfUnchanged` in `amplify/data/resource.ts` — run `create-ampless upgrade` and redeploy to enable conditional saves. The bundled themes build their `#post-body` (and home featured-post body) class with `ampless.postBodyClassName`, keeping the same base classes as before. THEMES.md documents post and table classes, editing them, and the concurrency guarantees.

Guarantees and non-guarantees: the admin editor's conditional save (upgraded backend; not a new-bundle static save) never overwrites a change made after the editor loaded the post. An MCP write with `expectedVersion` never overwrites a change made after the read the version came from, including a same-millisecond write by a stock or legacy writer (the token hashes the content, not just `updatedAt`). `set_post_classes` `add` / `remove` without `expectedVersion` never drop another writer's metadata change; they re-apply on top of it. Unconditional writers — `update_post` without `expectedVersion`, the static bundle tools, older clients, any direct GraphQL `updatePost` — can still overwrite anything. **Not addressed:** concurrency safety for static bundles (the static requirement of #411). A new-bundle save, from the admin or the MCP static tools, still overwrites the slug's S3 prefix in place and then saves the Post row unconditionally; the admin only does a read-only pre-check before the upload. Making that safe needs a separately reviewed design. A revision-history snapshot (keyed by `updatedAt`) can only collide when an unconditional writer saves in the same millisecond as another write.

Existing data is unaffected: `PostMetadata` gains no typed field (the new key stays `unknown` like any other free-form key), and a plain `metadata.postClasses` key — whatever a theme or plugin stored there — is neither read, rendered, nor written.

Static posts' bundle tools (`upload_static_bundle`, `commit_static_post`, ...) are unchanged apart from the additive `version` on the post they return, and remain unconditional.
