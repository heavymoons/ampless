Theme-declared custom classes for whole posts (heavymoons/ampless#380, phase 2; #402).

- `ampless`: `ThemeCustomClassTarget` is now `'table' | 'post'`. New helpers `themeCustomClasses(manifest, target)`, `themePostClasses`, `postCustomClassName` (`ampless-post--<id>`), `normalizePostClasses` and `postBodyClassName(metadata, base)`. `themeTableClasses` behaves as before. `PostMetadata` gains the reserved key `postClasses?: string[]`. Ids follow `CUSTOM_CLASS_ID_PATTERN`. `ThemeManifest` gains an optional `postBody?: { className?: string }` (type `ThemePostBody`): the base classes of the theme's `#post-body` wrapper, shared by the theme's post page and the admin preview.
- `@ampless/runtime`: `ampless.postBodyClassName(post, base?)` returns `base` plus `ampless-post--<id>` for each id in `post.metadata.postClasses`. Ids are re-validated on every call, so values written via MCP / GraphQL cannot break out of the attribute. Posts without classes get `base` back unchanged, so their markup is byte-identical.
- `@ampless/admin`: the post settings gain a "Post styles" section with checkboxes for the active theme's `target: 'post'` classes. It shows when the theme declares post classes or the post already has some. It is hidden for static posts and `no_layout` html posts, which bypass the theme's post body wrapper; their stored selection is kept. Stored ids the active theme does not declare (for example after a theme switch) are kept, still rendered, flagged as "not declared by the active theme" and removable with one click. They are never dropped silently. Once the user changes post styles, save writes `metadata.postClasses`, or removes the key when none are selected, and keeps the other metadata keys. Until then the stored value is kept exactly as it is, so saving an unrelated edit never rewrites or deletes it, even when it is not a clean id list (for example a non-array value from a plugin, or invalid or duplicate ids). Such a value shows a warning in the "Post styles" section (also when the theme declares no post classes): it is kept on save, and changing post styles there replaces it. Autosave drafts carry the selection only after the user changed post styles, so recovering any other draft keeps the stored value. Revision restore applies the revision's selection, and rewrites the key on save only when the revision's stored value differs from the current post's. The preview request now sends the edited metadata. The preview document now mirrors the public post page: it renders `<main id="post-body">` with the classes, sets `data-theme` to the active theme on `<body>`, and sets `data-color-scheme` on `<html>` when the site pins a colour scheme. The wrapper's base classes are the `bodyClassName` option of `createPreviewRouteHandler` when given, else the active theme's `manifest.postBody.className`, else the previous default. Attribute values are HTML-escaped. If the theme config cannot be loaded, the preview falls back as before and logs a warning. The client side of the preview copies only same-origin stylesheet links from the admin page, so external CSS is no longer pulled into the iframe, and it no longer copies a body `data-*` attribute the server already set, so the server's `data-theme` wins. `createEditPostPage` / `createNewPostPage` read the theme manifest once for both table and post classes.
- `@ampless/mcp-server`: `create_post` and `update_post` accept a top-level `postClasses: string[]`. Invalid ids, at the top level or in `metadata.postClasses`, are rejected with an error that names them. `create_post` merges the list into `metadata`. `update_post` with `postClasses` and no `metadata` reads the current post and merges, so `cache`, `no_layout` and plugin keys are not erased. The merge is atomic: the write is conditional on the post's `updatedAt` being unchanged since the read. If someone else saves the post in between, the call fails with an error saying nothing was written and asking to re-read and retry, instead of overwriting their change. It does not retry by itself. Other calls send no condition, as before. An empty array removes the key, and a missing post is an error. With both `metadata` and `postClasses`, the list is put into the supplied `metadata`, which still replaces the stored object as before. The tool descriptions and `get_schema` notes (`notes.postClasses`) document the key.
- `create-ampless`: all six stock themes declare their `#post-body` classes as `postBody.className` in `manifest.ts` (byte-identical to before) and pass them through `ampless.postBodyClassName(post, manifest.postBody?.className)`, and the blog / corporate / dads / landing home pages pass their own featured post wrapper classes through `ampless.postBodyClassName(featured, '…')`. `THEMES.md` / `THEMES.ja.md` describe post and table classes for custom themes. `create-ampless upgrade` replaces stock themes, so they pick this up automatically.
- `@ampless/backend`: the schema comment lists the new reserved metadata key. There is no schema change. The MCP handler's AppSync client attaches the raw GraphQL errors (with `errorType`) to the Error it throws as `graphqlErrors`, so `update_post` can recognise a conditional-write conflict. The error message is unchanged.

To use post classes in a custom theme:

1. Declare them in the theme manifest: `customClasses: [{ id: 'wide', label: { en: 'Wide', ja: 'ワイド' }, description: '…', target: 'post' }]`.
2. Style them in the theme's `tokens.css`, e.g. `.ampless-post--wide { … }` or `.ampless-post--wide h2 { … }`, optionally scoped under `[data-theme='<name>']`.
3. Move the post body wrapper's existing classes into the manifest as `postBody: { className: '<the existing classes>' }`, and change the wrapper in `pages/post.tsx` to `className={ampless.postBodyClassName(post, manifest.postBody?.className)}` (with `import manifest from '../manifest'`). Optionally pass the home page's featured-post wrapper through `ampless.postBodyClassName(featured, '<its classes>')`.

`my-*` copies and other custom themes are not touched by `upgrade` and need the edits in step 3. Without the `postBodyClassName` call, editors can pick post styles and they are stored, but the theme does not render them. Without `postBody.className`, the admin preview uses the default `prose prose-neutral dark:prose-invert max-w-none` base instead of the theme's.

Ids stay in the post when the active theme stops declaring them. They keep rendering as `ampless-post--<id>`, which is unstyled until a theme declares that id again.
