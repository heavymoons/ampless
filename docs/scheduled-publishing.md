# Scheduled publishing

ampless lets you write a post today and have it appear on your site at a
future date and time — without any manual action at publication time.

---

## How scheduling works

A post is scheduled by combining two things:

1. **`status: 'published'`** — the post is in the published state.
2. **`publishedAt`** set to a future UTC timestamp — the post is hidden
   from all public surfaces until that moment.

A published post whose `publishedAt` has already passed (or has no
`publishedAt`) is visible immediately.

A **draft** post is always hidden regardless of `publishedAt`. Setting a
future `publishedAt` on a draft has no effect until you change the status
to published.

```
status: 'draft'     → always hidden
status: 'published' + publishedAt: null     → visible now
status: 'published' + publishedAt: past     → visible now
status: 'published' + publishedAt: future   → hidden until publishedAt
```

---

## `publishedAt` semantics

### Missing `publishedAt` = immediate

When you hit **Publish** without setting a date, the admin editor and MCP
stamp `publishedAt` with the current server time. This ensures the post
appears in all listings — home page, tag pages, feed.xml — which sort and
filter by `publishedAt` descending.

### `publishedAt` is the public sort key

All public post listings (home page, tag pages, RSS feed, sitemap) order
by `publishedAt` descending and exclude posts whose `publishedAt` is in
the future. The `publishedAt` value stays fixed once set; it does not
change if you later edit the post body.

### Legacy rows without `publishedAt`

Sites that existed before scheduled publishing was introduced may have
published posts with no `publishedAt`. These posts:

- Are accessible via their direct URL (`/<slug>`).
- Do **not** appear in listings, the home page, tag pages, feed.xml, or
  sitemap.xml — they are invisible to the sort/filter logic.

To bring them into listings, open each post in the admin editor and save —
the editor will backfill `publishedAt` to the current time. Alternatively,
use the MCP `updatePost` tool with an explicit `publishedAt` if you want
to preserve an older effective date.

---

## Timing accuracy

Scheduled posts do **not** go live at an exact second. Visibility depends
on the cache window between the server and the browser:

- Public surfaces (post page, home/listings, tag pages) are Next.js
  server-side rendered with a cache TTL of up to **~5 minutes** by
  default (configurable via `cms.config.cache.freshTtlSeconds`).
- `feed.xml` and `sitemap.xml` are regenerated by the RSS / sitemap
  plugins when a `content.published`, `content.updated`, or similar event
  fires. Those events fire **at save time**, not at `publishedAt`. The
  feeds therefore refresh when the *next* content event occurs after
  `publishedAt` passes — not automatically at the scheduled time.

If exact-to-the-minute delivery matters (e.g. breaking news), schedule
the post slightly earlier than the target time and account for the cache
window.

---

## Event and notification timing

The `content.published` event is emitted via DynamoDB Streams **when the
post is saved to the database**, not when `publishedAt` arrives. This
means:

- Outbound notification plugins (webhook, push notification, social post)
  will fire as soon as you save the post — potentially hours or days
  before the post is publicly visible.
- Plugins that rebuild public assets from the current post list (RSS,
  sitemap, JSON indexes) are unaffected: `listPublishedPosts()` already
  excludes future-dated posts.

Plugin authors should guard outbound notifications with a `publishedAt`
check. See the plugin-author guide for the recommended pattern:
[`packages/ampless/docs/plugin-author-guide.md` §6a](https://github.com/heavymoons/ampless/blob/main/packages/ampless/docs/plugin-author-guide.md#6a-scheduled-posts-and-content-events).

## Date/time format

All `publishedAt` values are **UTC ISO 8601** strings ending in `Z`, for
example `2026-09-01T09:00:00.000Z`. When using the MCP `listPosts` or
`listPublished` tools with `from` / `to` query arguments, pass canonical
UTC ISO strings (ending in `Z`). Timezone-offset forms
(`2026-09-01T18:00:00+09:00`) are not guaranteed to be accepted by all
query paths.

## Upgrade notes for existing deployed sites

Scheduled publishing requires changes in two independent places. **Both**
must be deployed; doing only one leaves the other surface leaking future
posts.

### 1. AppSync resolver files (per-site, not in `@ampless/backend`)

The listing and single-post resolvers live in your site repo under
`amplify/data/` as `.js` files. These are copied from
`templates/_shared/amplify/data/` by `create-ampless` and are **not**
updated by `@ampless/backend` package upgrades — they are part of your
site's source.

Update the relevant resolver files from the latest
`templates/_shared/amplify/data/` source, then **redeploy** (`amplify push`
or sandbox restart). Until this is done, the AppSync layer does not filter
future `publishedAt` rows on single-post fetches.

### 2. `@ampless/backend` package

The `listPublished()` helper used by `feed.xml` and `sitemap.xml` lives in
`@ampless/backend`. Bump to the version that includes the scheduled
publishing filter, then redeploy. Until this is done, `feed.xml` and
`sitemap.xml` may include future-dated posts.

### Checklist

- [ ] Update `amplify/data/*.js` resolver files from the latest template
      source and redeploy.
- [ ] Bump `@ampless/backend` to the minimum version that includes
      scheduled publishing support and redeploy.
- [ ] Verify: create a post with a future `publishedAt`, confirm it does
      not appear in the home listing, tag pages, feed.xml, or sitemap.xml
      before the scheduled time.
